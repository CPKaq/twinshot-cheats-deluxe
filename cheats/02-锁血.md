## 1. 效果定义

- 玩家看到的最终效果:攻击生效时不扣血
- 生效范围:所有攻击
- 与"无伤(01)"的语义区别:锁血开启时**受击反馈保留**(音效/闪烁/击退),但血量不减、永不触发 `Kill()`;无伤则连受击判定都不发生

### 关键代码摘录(附 dnSpy 行号)

```csharp
[NonSerialized]
public int hits = 2;

//                   where p != null select p).ToArray();

// Token: 0x060000E1 RID: 225
public bool AreAnyPlayersAlive()
{
    Player[] array = this.players;
    for (int i = 0; i < array.Length; i++)
        if (array[i].alive) return true;
    return false;
}

// Token: 0x06000402 RID: 1026 RVA: 0x000300C0
public bool Hit(Vector2 positionOfOtherObject)
{
    ...
    {
        this.hits--;                    // ← 扣血点
        if (this.hits < 1)
            this.Kill(false);           // ← 死亡分支:锁血时永不触发
        else
            Audio.instance.PlayHitSfxForPlayer(this);

}
```

**读取链结论(经 field dump 修正)**:`Level.Instance` 是**属性**而非字段(实现为 `return Game.instance != null ? Game.instance.level : null`),Level 类没有任何静态字段。
trainer 实际走:`Game.instance`(静态字段)→ `Game.level`(实例字段,当前关卡)→ `Level.players`(`Player[]`)→ `Player.hits`(int)。
x64 mono 数组布局直读:数据区 `+0x20`,`max_length` 在 `+0x18`(8 字节)。
通用教训:**dnSpy 里看到的 `X.Instance` 这类单例用法,先确认是字段还是属性;是属性就找它的数据来源类,用"静态字段 + 类型匹配兜底"定位**。

## 3. 实现选型(Phase 3)

- [x] 写字段(锁数值)-> 需要每帧/事件触发?**是:tick 每 30ms 写回快照值**
- [ ] patch 方法(直接返回或改参数)
- [ ] 调用游戏自己的方法(如清除状态)

**选型:写字段 + tick 持续写回**(trainer 框架的 `Lock_Tick` 槽位就是为此设计的)。

理由:
- patch `Hit(Vector2)` 已经被"无伤(01)"占用;锁血要保留受击反馈,只有不拦方法、只锁值;
- `hits--; if (hits < 1) Kill()` —— 只要 tick 保证 hits 恒 ≥ 1(实际锁快照值),死亡分支永不触发,受击动画/音效完全原生;
- 关闭锁血 = 停止写回,立即恢复自然扣血,无需还原任何字节。

**锁定值策略**:开启瞬间逐玩家**快照当前 `hits`**,之后写回快照(兼容自定义血量);revert 时清空快照。

**遗留的关键问题:活实例来源**(写字段的前提)——dnSpy 排查中,候选:
1. `Player` 的静态集合字段(Nitrome 常用 `static List<Player> list` 模式);
2. `Level.Instance`(单例,已在 Hit 代码中出现)下挂的玩家列表/数组;
3. 都没有则考虑:hook `Player` 构造函数入口捕获 `this`(x64:实例方法 `this` 在 RCX)——备选方案,复杂度高,先不走。

## 6. 实测记录

### 第一次实测:失败,超时

日志:`lock: field resolution failed (Instance/players/hits)` × 240 次 → NOT ready。同时暴露两个缺陷:

1. **定位失败的具体原因没有细分**(三个字段哪个 MISS 不知道);
2. **无伤被锁血的重试拖住 60 秒**才默认开启——定位循环设计缺陷(ready 后应立即默认开启)。

### 修复(第二轮)

- 无伤迟到:**已修**,ready 即 ON(default),不再等全员;失败日志节流(每 16 次 1 条);
- 定位失败:**首要嫌疑 `Level.Instance` 是属性而非字段**(`Level.Instance.ended` 是用法,不证明它是字段;若是 `static Level Instance { get; }`,后备字段名形如 `<Instance>k__BackingField`,`mono_class_get_field_from_name("Instance")` 找不到)。
  修复措施:
  1. 兜底:自动扫描"static 且类型含 `Level`"的字段作为单例;
  2. 仍失败:首次失败时 **dump `Level`(及需要时的 `Player`)全部字段**(名字+类型+static 标记)进日志,人工比对一次即可定位真名;
  3. 失败原因细分日志:`resolve failed (Instance=MISS players=ok hits=ok)` 这样的格式。

### 第二次实测:dump 定位到真相

- 无伤修复验证 ✅:ready 即 `ON (default)`,不再被锁血拖住;
- 锁血仍失败,但 field dump 提供决定性证据:
  - Level 全部 29 个字段均为实例字段(`0x0086` = Public + NotSerialized),**没有任何 static**;
  - 用户在 dnSpy 找到 `Level.Instance` 定义:`public static Level Instance { get { ... return Game.instance.level; } }` → **属性**,数据根在 `Game` 类。

**新数据链**:`Game.instance`(静态)→ `Game.level` → `Level.players` → `Player.hits`。
实现更新:LockCtx 换为 `fGameInstance / fLevel / gameVt`;`Game.instance` 与 `Game.level` 均带"按类型匹配"兜底(精确类名或 `命名空间.类名` 后缀);失败时 dump `Game` 类。

### 待复测结论

- **复测成功 ✅**:数据链 `Game.instance → Game.level → Level.players → Player.hits` 生效;实测语义符合预期(击退、丢失道具等受击效果保留,血量不变),日志快照数值正确;
- `Game.instance` 与 `Game.level` 均一次命中("instance"/"level" 字段名,无需类型兜底);field dump 方案作为版本更新的诊断手段保留。
